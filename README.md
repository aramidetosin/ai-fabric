# ai-fabric — AI cluster lab: Cumulus frontend + OcNOS rail backend + refplat-style Kubernetes nodes

Runs under containerlab on a single host; clone it anywhere and set the profile (see `RUNBOOK.md`). Everything is generated by
`gen.py` — edit `gen.py`, never its outputs. Values that no reference design fixes are marked `LAB` in `gen.py`.
Throughout, **refplat** means the reference platform this lab mirrors: the upstream Kubernetes-on-containerlab build whose node
images, management subnet and manifest set are reused here. You do not need it to run this lab.

## Profile `site-a-nx`: Cisco Nexus frontend with vPC Fabric Peering (office, since 2026-09-23)

The office lab with its Cumulus frontend replaced by **Cisco Nexus 9300v** (`<your vrnetlab tag>`). Everything else
is unchanged: OcNOS backend, vEX OOB switch, firewall, guests, addressing. Switch back with `echo site-a > profile`, then `./down.sh` and `./up.sh`.
Proven first on a 7-switch copy (`../ai-fabric-nx-probe`, 142 checks, failover and reload tests), then on the light topology (145/145).

**Operator decisions (2026-09-23):**

| Area | Decision |
|---|---|
| Frontend switches | 2 spines (64-port) + 6 leaves (32-port): two GPU pairs of 16, and one control pair carrying ctrl1-6, the bastion (port 9) and the storage node (ports 10-13, 4 per leaf, one bond, VLAN 100 tagged; management FM1 / FM2 on port 14 of each leaf, see VLAN design). The separate storage pair is gone. |
| Border | A **separate border pair**, no vPC: a routed /30 to the firewall, as before. |
| Dual-homing | **vPC Fabric Peering** on the three pairs: a virtual peer-link over the spines between loopback2 addresses, no leaf-to-leaf cabling, keepalive over mgmt0 (lab value). |
| Underlay | **OSPF area 0, IP unnumbered** (loopback0), one link per spine, 1 s hello / 3 s dead. A shut port does not drop carrier on a virtual wire, so the dead timer is the failure detector. |
| Overlay | **iBGP EVPN**, private AS 65100 (lab value), spines as route reflectors, ingress replication. |
| OOB switch | Stays a vEX. |

**Forced by NX-OS, not choices:**

- VNIs start at 4096: L2 VNI = 10000 + VLAN, L3 VNIs 11000 / 12000 / 13000 (lab values; see the VLAN design table).
- The anycast gateway is the subnet's `.1` itself on every leaf, with MAC `000a.00c1.0001`; there are no per-leaf SVI addresses.
- NX-OS keeps **one SSH key per user**: `admin` holds the Mac key and `ops` (key-only, no usable password) holds the lab host's key. The scripts log in as `ops`.
- The borders present **AS 65104** to the firewall (`local-as 65104 no-prepend replace-as`). The PA-VM boots from the operator's `bootstrap/fw-override.xml`, which peers with 65104; the VLAN design is merged into it by `fw-merge-vlans.py`.
- Server ports run `lacp rate fast`. Without it, a server leg that failed on the server side blackholed that leaf's flows for 11 s; with it, 0.4 s.

**Boot sequence and new scripts:**

- vrnetlab types `configs/<switch>.cfg` into each switch.
- **`nx-wait.sh`** waits for health plus key login.
- **`nx-tcam-reload.sh`** reloads the six vPC leaves once per deploy. vPC Fabric Peering needs the `redirect` TCAM region at 512, and that only becomes active after save + reload. Every deploy is a first boot, and `show hardware access-list tcam region` shows the configured size, not the active one, so the script compares switch uptime with container age.
- `nx-tcam-reload.sh` then waits for vPC delay-restore (150 s) and the NVE source hold-down (180 s, during which the pair VIP is not advertised). Only then does `up.sh` release the guests.
- **`nx-checks.sh`** is the Nexus section B of `validate.sh` and the frontend part of `validate-fabric.sh`. Every expectation comes from `gen.py`:
  - every generated config line is present;
  - OSPF, unnumbered links, ECMP and LLDP cabling;
  - EVPN, NVE peers and VNIs;
  - vPC state, fabric ports, vPCs and bundled members;
  - the TCAM carve is active;
  - the anycast gateway, /32 host routes and the storage trunk;
  - firewall eBGP plus the default route, and the type-5 default on the leaves.
- `lib.sh` has `NX()` plus Nexus branches for every `fe_*` helper. The traces use the profile's L3 VNI and call the dual-homing vPC. Drill 2 allows 20 lost packets on Nexus (OSPF dead timer; BFD profiles allow 15).

**NX-OS gotchas found on the way:**

- An NX-OS SSH exec session does not end when its reader closes the pipe early (`| awk '...exit'`, `grep -q`, `head`); it hangs until the timeout. Helpers buffer the whole output first.
- `show bgp l2vpn evpn summary` prints the neighbour table twice.
- `show port-channel summary` wraps members after three ports.
- `snmp-server enable traps link` is a hidden default.
- "Last reset Reason" stays `Unknown` after a CLI reload.
- **First-boot kernel panic** (seen once, fe-gpu-leaf4, 2026-09-23): `BUG: kernel NULL pointer dereference` ~25 s into the first boot, reboot, then `grub failed` and `loader >` for good. Recovery without a redeploy: `docker exec clab-ai-fabric-<node> rm -f /n9kv-*-overlay.qcow2` and `containerlab restart -t ai-fabric.clab.yml -n <node>` (keeps the links; the launcher creates a fresh overlay, ~4 min to "Startup complete"). **Do not kill QEMU inside the container**: after its 300-spin timeout this vrnetlab launcher restarts QEMU without resetting the counter and loops every 6 s.
- 9300v RAM: budget the full **10 GB per switch**. The probe showed 4.5-7.1 GB, but in the full lab every switch's QEMU settled at ~10.1 GB, all of its allocation.

### VLAN design (operator, 2026-09-23)

Three VLANs on the frontend, each its own VRF with the fabric anycast gateway. **Everything between VLANs goes through the firewall**: each VRF reaches
the firewall on its own dot1q sub-interface of the border /30 links (fe-border1 Eth1/3 <-> ethernet1/1, fe-border2 Eth1/3 <-> ethernet1/2), and the
parents carry no address. VLAN 100 moved from the untagged link to `.100` on 2026-09-23 (operator: "move to .100", zone renamed `fabric` -> `data`).

| VLAN | Use | VRF / firewall zone | Subnet, gateway | L2 VNI / L3 VLAN / L3 VNI | Route targets | Border <-> firewall (.1 border, .2 firewall) |
|---|---|---|---|---|---|---|
| 100 DATA | k8s nodes, storage data | `k8s` / `data` | 10.1.1.0/24, .1 | 10100 / 3001 / 11000 | 100:100, 1000:1000 | `.100`: 10.1.254.0/30, 10.1.254.4/30 |
| 200 STOR-MGMT | storage management FM1 10.1.20.11 (fe-ctrl-leaf1 Eth1/14), FM2 .12 (fe-ctrl-leaf2 Eth1/14), no bond; API VIP **10.1.20.18** | `stor-mgmt` | 10.1.20.0/24, .1 | 10200 / 3002 / 12000 | 200:200, 2000:2000 | `.200`: 10.1.254.8/30, 10.1.254.12/30 |
| 300 BASTION | bastion 10.1.30.17 | `bastion` | 10.1.30.0/24, .1 | 10300 / 3003 / 13000 | 300:300, 3000:3000 | `.300`: 10.1.254.16/30, 10.1.254.20/30 |

- **Policy**: 100 -> 200 tcp/443; 300 -> 100 and 300 -> 200 tcp 22/80/443/6443; every VLAN -> DNS/NTP and internet (source NAT); everything else denied and logged (`deny-all-log`). Rules: `data-to-stor-mgmt`, `bastion-to-data`, `bastion-to-stor-mgmt`, `stor-mgmt-to-internet`, `bastion-to-internet`, `*-intrazone-bgp` (the firewall's own BGP). Kept: enterprise (pc-1/pc-2), OOB/BMC, office-LAN access to the platform, data -> enterprise.
- **DNS / NTP**: the office server dns-b (10.80.15.53). Nodes and the bastion reach it through the firewall (their VLAN -> internet rules); the switches AND the firewall itself use their management ports (operator 2026-09-23). Do not route the firewall's own DNS/NTP out of a data-plane port: PAN-OS then evaluates it as intrazone internet -> internet and `deny-all-log` drops it (seen in the traffic log as 10.80.15.121 -> 10.80.15.53:53). `ssh -t <host> /root/ai-fabric/fw-dns-mgmt.sh` removes such service routes from a running firewall (prompts for the password). The bastion no longer serves DNS/NTP. The lab zones live on dns-b: `./dns-b-zones.sh` (run on the Mac; own directory + one include line, checked before reload).
- **Firewall config**: `gen.fw_vlans()` is the one transformation, applied to `bootstrap/fw.xml` by gen.py and to the operator's capture by `python3 fw-merge-vlans.py bootstrap/fw-override.xml <out>` (prints every change, idempotent). The BGP peer-group keeps the name `fabric` (it is not a zone). Backups: `.bak-20260923-prevlans/`, `.bak-20260923-pretag100/`.
- **Nodes**: `CILIUM_DEVICES=bond0,bond0.100`; `cilium-devices.sh` (run by finish.sh) upgrades an existing Cilium when the list changed **and then restarts the agents**: they read `cilium-config` only at start, and a `--reuse-values` upgrade that changes only the ConfigMap does not roll the DaemonSet. Missed once (2026-09-23): every agent kept `bond0.10`, and the storage node (the only guest whose data address sits on the tagged `bond0.100`) lost service translation, so multus/whereabouts/Longhorn/MinIO there could not reach 10.43.0.1, Harbor stalled, and its host traffic to 10.43.0.1 leaked out through the firewall. `CHECK=1` now also fails when any agent is older than the ConfigMap's last write.
- **Office workstations** (one Windows, one Ubuntu): operator decision 2026-09-23 = hosts file only, their DNS servers stay as they are. The kit's `hosts-block.txt` maps every HTTPRoute name to the firewall outside address and adds `10.1.1.20 api.lab.ai` (tcp/6443 is allowed from the office LAN). node.env is distributed by `node-sync.sh` (cloud-init writes it only once).
- NX-OS writes consecutive VLANs as ranges (`3001-3003`); gen.py emits that form so the config-line check matches.

### Lab CA on dns-b (operator decisions 2026-09-23)

```
ai-fabric Lab Root CA        dns-b /root/ai-fabric-ca (RSA 4096, 10 y, pathlen 1; key 0400, no passphrase by decision; every signing kept in issued/)
 ├─ ai-fabric Platform CA    ECDSA P-256, 5 y, pathlen 0, name constraints DNS lab.ai, IP 10.1.0.0/16 + 172.21.21.0/24
 │    = cert-manager secret cluster-ca (ClusterIssuer cluster-ca): *.platform wildcard (90 d), storage-mgmt.lab.ai + 10.1.20.18, fw-mgmt.lab.ai + 172.21.21.30 (1 y)
 └─ ai-fabric Kubernetes CA  RSA 2048, 5 y, pathlen 0, name constraints DNS lab.ai, kubernetes(.default(.svc)), cluster.local, ctrl1-3, IP 10.0.0.0/8
      = kubeadm /etc/kubernetes/pki/ca.{crt,key} (etcd + front-proxy CAs stay kubeadm's own)
```
- **Why name constraints on both**: the root is trusted by the office workstations; an unconstrained intermediate would let whoever holds its key mint a trusted
  certificate for any site. `dns-b-ca.sh` proves it: leaves for other domains/addresses are rejected ("permitted subtree violation").
- **Keys**: the intermediates' keys live in the lab host's **host-only** `ca/` (0700), never in `shared/` (a read-write 9p mount on every guest). gen.py binds
  `ca/` read-only into the **init node's container only**; vm-init turns it into cloud-init `write_files` (`/etc/ai-fabric/ca`, keys 0600), which run before the
  bootstrap. ctrl2/3 receive the Kubernetes CA through kubeadm's certificate upload, like any kubeadm HA join.
- **Bootstrap**: `place_k8s_ca` puts the Kubernetes CA in place before every `kubeadm init` attempt; `chain_apiserver` appends it to `apiserver.crt` on each
  control plane (re-checked every run: `kubeadm certs renew` rewrites the file without it) so a client that trusts only the root verifies `api.lab.ai:6443`.
  cert-manager's `cluster-ca` secret is the Platform CA with `ca.crt` = the root, so the published `/shared/ai-fabric/cluster-ca.crt` IS the root: the
  workstations, PCs, bastion, containerd and the publish kit trust it once, for good. Without `ca/` (other profiles) nothing changes: `pki-selfsigned-ca.yaml`.
- **Scripts**: `dns-b-ca.sh` (Mac: root once, intermediates signed when missing/mismatched/expiring within 90 d, proof run); `ca-certs.sh` (finish stage 6:
  storage + firewall leaves, the storage node pulls its own; `CHECK=1` in validation); `fw-ui-cert.sh` (operator, `ssh -t`, firewall password: imports the UI
  certificate, then run `fw-backup.sh`). `pvc-tool.sh` verifies the storage API when `FB_CACERT` is set (validation + trace-pvc do).
- **Renewal**: intermediates expire 2031 (re-run `dns-b-ca.sh`), root 2036. cert-manager renews the storage/firewall leaves 30 days before expiry: then re-run
  `ca-certs.sh` (storage node) and `fw-ui-cert.sh` (firewall); validation flags anything expiring within 30 days.

### NVIDIA network-operator on the simulated GPU nodes (operator decisions 2026-09-24)

The production GPU cluster's stack, as close to verbatim as virtio NICs allow. `finish.sh` stage 7 runs `rdma-prep.sh` then `netop.sh` (profile
service `network-operator`); everything is idempotent and rebuilt by a redeploy.

| Piece | Lab | Production |
|---|---|---|
| operator | chart/image **v26.1.1** (NGC), namespace `nvidia-network-operator`, bundled NFD off | v26.1.1, `oik8s-nvidia-network-operator` |
| NFD | **separate** release `nfd` (upstream chart 0.18.3), namespace `node-feature-discovery`, worker tolerates the GPU taint | separate `oik8s-node-feature-discovery` |
| rails | `MacvlanNetwork net-rail-0..7`: master `gpu0..7`, bridge, MTU 9000, NAD in `default`; whereabouts `172.16.(N+1).0/24`, gateway `.1`, exclude `.1/32` + node block `.0/26`, **no routes** | `net-rail-0..15` on `enp…np0/np1`, `10.21.5x.0/24`, exclude `.1/32`, no routes |
| NicClusterPolicy | `nodeAffinity` **verbatim** (gpu, worker, `pci-15b3.present`); `rdmaSharedDevicePlugin` same image/version, `rdma_shared`, `rdmaHcaMax 63`, selector `ifNames gpu0..7` | + `ofedDriver` DOCA 3.2.2, selector `vendors 15b3` + 16 ifNames |
| RDMA devices | **SoftRoCE** `rxe_gpuN` on each rail NIC (`rdma_rxe` from linux-modules-extra; netsetup.sh at every boot) | ConnectX (mlx5) |
| `pci-15b3.present` | faked by NodeFeatureRule `ai-fabric-fake-pci-15b3` (kernel module `rdma_rxe` loaded) | NFD PCI discovery |
| images | through Harbor `proxy-nvcr` (+ `proxy-k8s` for NFD) | `registry.platform.ai.dev.mil.ae` |

- **Forced deviations**: no `ofedDriver` (no Mellanox hardware); no `15b3` vendor selector (virtio is `1af4`); `mlx5_core` is loaded without hardware
  because the plugin's init container waits for it (`lsmod | grep mlx5_core`); rail subnets are the OcNOS fabric's `172.16.x`; the IPAM also excludes
  the nodes' own rail addresses.
- **Production shape = same rail only**: the MacvlanNetworks carry no routes, so a pod's rail interface reaches only its own rail (the bootstrap's
  old `gpu/rail-1..8` NADs, which added a `172.16/16` route, are replaced). Validation section G and `trace-rail.sh` test same-rail paths (+ jumbo) and
  assert the separation; the spines carry no pod traffic in this shape.
- **SoftRoCE probe** (`rdma-probe.sh`, part of `validate-all.sh`), rail 1 between gpu1 and gpu2, in layers. Result 2026-09-24 (kernel 6.8.0-138):

  | Layer | Result |
  |---|---|
  | rdma-shared-dev-plugin discovery | **KNOWN**: 0 devices. The plugin walks the PCI network devices and looks for RDMA devices under `/sys/bus/pci/devices/<nic>/infiniband`; `rxe_gpuN` lives under `/sys/devices/virtual/infiniband` (no PCI parent). Pods run privileged with `/dev/infiniband` mounted instead of requesting `rdma/rdma_shared` |
  | host to host, verbs and RDMA CM | PASS, ~6.4 Gbit/s each (software RoCE on a VM: proves the path, not a speed) |
  | pod macvlan address as a RoCE GID | PASS: the pod's `net-rail-0` address appears in `rxe_gpu0`'s GID table, as with ConnectX |
  | pod to pod over the pods' own macvlan GIDs (production's path) | **KNOWN**: completion error (flush). `rdma_rxe` before **v7.1** is `init_net`-only (route lookup + UDP 4791 socket); upstream netns support is commit 13f2a53, first in v7.1. The 24.04 HWE kernel on offer is 7.0, which lacks it |
  | pod to pod through the shared device with the host rail GIDs | PASS, ~6 Gbit/s: pods do drive RDMA on the rail through the shared rxe device |
  | RDMA CM from a pod | **not run** (KNOWN): on rxe before v7.1 it puts the device's GSI QP (QP1) into `ERR`, and RDMA CM on that device then stays dead for the host too until the device is re-created. NCCL uses verbs + its own socket exchange, not RDMA CM |

  `netsetup.sh` re-creates any `rxe_gpuN` whose QP1 is in `ERR` (every boot / node-sync / rdma-prep); `rdma-prep.sh CHECK=1` (validation section G)
  fails a node that has one.
- **Visibility**: `audit.sh` collects the NicClusterPolicy, MacvlanNetworks, NADs, operator pods, Helm releases, NodeFeatureRules, per-node
  `pci-15b3` + `rdma_shared`, and on the GPU hosts `rdma link`, the GSI QP state per device, the RDMA modules and `/dev/infiniband`;
  `netop.sh CHECK=1` and `rdma-prep.sh CHECK=1` are the reports validation uses.

## Persistence: from nothing, across redeploys, across a host reboot
`./up.sh` is the ONLY command between a prepared host and a fully working lab; nothing is fixed by hand afterwards.

| Step | What | Where the state lives |
|---|---|---|
| `host/install.sh` (once per host) | checks the prerequisites, installs + enables `ai-fabric-lab.service` | `/etc/systemd/system/ai-fabric-lab.service` (undo: `host/uninstall.sh`) |
| `./up.sh` | registry caches, local images (**rebuilt whenever `images/**` is newer than the image**, not just when one is missing), `containerlab deploy` with the guests HELD, Junos configs (`apply-junos.sh`), `wait-fabric.sh`, guests released, then **`finish.sh`** | switches + firewall: always from `gen.py` (`configs/`, `bootstrap/fw.xml`) |
| `finish.sh` (9 stages, idempotent, log `finish.log`) | switches healthy -> bootstrap finished -> guests' boot-time files = repository (`node-sync.sh`) -> all nodes Ready -> fabric settled (east-west sweep until two clean rounds) -> roles (`roles.sh`) -> profile services (Harbor + S3 + Longhorn backup target + containerd trust) -> every pod Running -> workstation kit + the operator steps still open | guests: `nodes/<n>/vm/root.qcow2` + `data.img` (etcd, Longhorn replicas, the S3 disk, Harbor's database, the operator's secrets) |
| host reboot | `ai-fabric-lab.service` runs `boot.sh` (**site-b only — site-a is deliberately manual, run `./boot.sh` yourself; that host also runs the user's EVE-NG VMs and 39 guests claiming ~200 GB at boot once OOM-killed them**): removes the link-less containers the reboot left, deploys again ON THE EXISTING DISKS, `finish.sh`, then `validate.sh` (result set in `audits/`, verdict in `boot-status`, log `/var/log/ai-fabric-lab.log`) | survives: everything in Kubernetes. Rebuilt from the generator: switches, firewall, bastion, PCs |
| host shutdown / `./down.sh` | `stop.sh` powers the guests off inside the guest (GPU + workers, then storage, then the control plane); a QEMU guest gets no ACPI signal from `docker stop` | `./down.sh fast` skips it, `./down.sh wipe` deletes the disks = next `./up.sh` starts from nothing |

Why `node-sync.sh` exists: cloud-init writes the files a guest runs AT EVERY BOOT (`netsetup.sh`, the two units, the networkd drop-in; on the init
node also `cluster-bootstrap.sh` and its manifests) once, at the guest's first boot. A fix made here later would never reach an existing disk, and the
next guest reboot would bring the old behaviour back. `node-sync.sh` keeps all guests equal to `images/vm-node/` (`CHECK=1` only reports; validation
section A checks it). Found with `host/reboot-test.sh` and fixed that way:
- the init node re-ran an old bootstrap that put every node back into the control class (GPU nodes announcing the Gateway VIP again). The bootstrap
  now produces the final node classes itself and retries every manifest apply (a 39-node rollout makes the API time out now and then);
- `ai-fabric-netsetup` ran BEFORE systemd-networkd on a reboot (on the first boot cloud-init starts it late, which hid it): no management
  address yet -> a second default route on `eth0`, and networkd then removed every policy-routing rule (management table 150, OOB table 100,
  the eight rail tables). Now ordered after `network-online.target`, waits for `eth0`, and networkd leaves foreign rules/routes alone
  (`ManageForeignRoutingPolicyRules=no`, also what Cilium asks for).
- guests on existing disks are up in a minute and bring LACP, MAC learning and ARP onto vEX switches whose EVPN/ESI configuration is still being
  committed: twice this left a vEX data plane with a stale entry (control plane correct; one leaf silently dropped everything for ONE server's ESI
  MAC). `up.sh` now HOLDS the guests (`shared/hold-guests`, honoured by `vm-init.sh`) until `wait-fabric.sh` sees every frontend EVPN session
  established twice in a row; `finish.sh` stage 5 sweeps east-west AND the routed path from the enterprise PC until three clean rounds and bounces
  the fabric links of a node that keeps losing (EVPN withdraw + re-advertise = the repair that worked);
- latent since day one, exposed by the new sweep: in vrf `k8s` only ONE of a leaf pair's two equal type-5 routes per host prefix was active, so
  a border built a VXLAN tunnel to that leaf only and dropped L3-VNI packets arriving from the pair's OTHER leaf (no tunnel for that source VTEP).
  Pairs with many hosts got lucky; the storage pair (one host) lost every flow hashed to `fe-stor-leaf2`. Fix: `routing-instances k8s
  routing-options multipath` on every vEX. The old check pinged one node (and a hard-coded storage address): section D now pings EVERY node.
`host/reboot-test.sh` reproduces a host reboot without rebooting the host (shutdown hook, docker stop, policy restarts without links, unit start).
Operator steps stay operator steps after a `wipe` (keys never pass through the scripts' logs): `post-deploy.sh`, `harbor-password.sh`, `secrets-to-s3.sh`;
`finish.sh` lists the ones still open. One-off opt-out of the boot start: `touch no-autostart`. Validation section A carries the persistence checks.

Firewall web UI without a tunnel (profile `site-b`, key `fw_ui`): `https://192.168.1.250:8443/` = DNAT on the outside address to `loopback.1`
(`10.1.254.254`, LAB) with an HTTPS management profile limited to `192.168.1.0/24`; rule `internet-to-fw-ui`, NAT `dnat-fw-ui`. The management
address `172.21.21.30` stays reachable from the lab host only (and is the OFFICE firewall's address from the Mac, which routes that subnet there).

**Host memory watchdog (site-a).** `/root/mem-watchdog.sh <floor-MB>` + `/root/mem-watchdog.on`: while the marker file exists it polls `MemAvailable`
and stops the highest-numbered GPU guest whenever the floor is crossed, so a rollout that does not fit degrades the LAB instead of letting the kernel
OOM-kill whatever it likes on a shared host. Log `/root/mem-watchdog.log`. Turn it off with `rm /root/mem-watchdog.on`.

**Traps** go to the lab host's management address `172.21.21.1:162` on both hosts (`gen.py` `SNMP_TRAP_HOST`), because that is an address every device can reach:
- site-a already DNATs udp/162 to the Weft VM: traps arrive with the device's own 172.21.21.X source = the address Weft knows for Site-4. Verified: all 11 Cumulus, 13 servers, 2 PCs.
- site-b relays them in `host/weft-alias.nft` (operator-installed): DNAT to site-a's Tailscale address + source mapped 1:1 to the alias 172.21.121.X, so Weft attributes them to the Site-3 device. site-a needs `host/weft-alias-office.nft` chain `keep_trap_source` (priority srcnat - 10): without it Tailscale's subnet-router masquerade turns every home trap into 172.29.129.254. Verified: test traps from switches, servers, bastion and PCs of both sites arrive once each with their own address and Weft files them under the right site/device.
- Junos: traps through the SNMP target/notify framework (v2c, `mgmt_junos`) with notify-filter `NOLICENSE`, NOT a trap-group: unlicensed vJunos sends a jnxLicense trap (`1.3.6.1.4.1.2636.3.63.1.0.5`, "VXLAN") every 10 s from every VXLAN switch whatever the trap categories are; only a notify-filter can drop it. Everything else (link, BGP, start, authentication) goes through. Cumulus: link up/down + authentication failures. Servers/bastion/PCs: coldStart + authentication failures ONLY (link traps on a Kubernetes node would report every pod veth).
- **OcNOS VM: configured (`snmp-server host ... vrf management`, traps link/bgp/authentication) but the demo VM never emits a trap** (captured inside the container: zero udp/162 on an agent restart and on an authentication failure). ## Deviations from the references, and why
**Backend (vs AI_FABRIC Cluster-1 800G AI configs)**
- **eBGP instead of iBGP AS 1 + route reflectors** (spines AS 65200, leaf L = 65200+L) — decided with the operator. On the OcNOS VM BGP
  unnumbered never leaves Idle; a route reflector does not rewrite next-hops (`next-hop-self` and an outbound `set ip next-hop` are both
  ignored for reflected routes); and the VM kernel refuses multipath over recursive next-hops. iBGP+RR therefore forwards over one spine
  only. eBGP restores adjacent-spine next-hops and production's own `max-paths ebgp 64` gives 4-way ECMP.
- Numbered /31 underlay `10.255.<spine>.x`; leaves filter those /31s out of `redistribute connected`, so they advertise rails + loopback only —
  the prefix set production advertises.
- Not available in the VM CLI (hardware only), left out: `load-balance rtag7 *`, `dynamic-load-balance enable`, `fault-management enable`,
  `default-interface load-interval`, `vlan-reservation`, port breakout, `qsfp-dd`. `maximum-paths 64` needs a reboot (VM default 8 is enough).
  `qos enable`, `data-center-bridging enable`, `priority-flow-control enable`, `fall-over bfd` are accepted — but a VM cannot enforce lossless.
- MTU 9198, not 9216 (VM maximum). **A rail SVI cannot exceed MTU 1500 on the VM** (every `mtu` above it is refused), so jumbo 8972-byte DF
  frames pass on the SAME rail (L2) but the routed cross-rail path is capped at 1500; the destination leaf answers frag-needed, so path-MTU
  discovery works. The test suite reports this as KNOWN, never as a pass. Production carries `mtu 9216` on the SVIs: verify cross-rail jumbo on hardware.
- The unprivileged SSH prompt refuses half of the show commands; `enable` needs no password, so `OCE` (lib.sh) runs audits and drill changes
  in privileged exec over SSH. Hardware-only shows (`show interface counters`, `show qos`) do not exist on the VM.
- Added: `line console 0 / exec-timeout 0 0` and `username admin sshkey …` so the nodes stay manageable without typing credentials.

**Frontend (vs reflab and AI_FABRIC Cluster-1 100G)**: Cumulus NVUE instead of OcNOS; one flat VLAN as requested; ASNs, loopbacks, per-leaf SVI
addresses `.2-.7`, L3VNI VLAN 3001 and the /30s to the firewall are LAB values. BFD (3 x 300 ms, PTM-based on Cumulus: `ptmctl -b`) runs on
every underlay session like production's `neighbor IPV4_UNDERLAY fall-over bfd`: without it drill 2 measured 7.6 s of east-west loss when a
spine failed silently (BGP hold time 9 s); with it 0.8 s.

**Hosts (vs refplat)**: image `ai-fabric-vm-node` = refplat's vm-node plus `RAIL_NICS`: eight REAL rail NICs (container `eth4-eth11` → guest `gpu0-gpu7`,
refplat used unwired dummies) with per-rail source routing, and the rail NADs carry the rail gateway. `ai-fabric-bastion` = refplat's bastion with the
chrony allow-list parameterised. Two external PCs instead of refplat's one inside / one outside.

## Things that bit during the build
- One rejected value in an OcNOS candidate config silently fails every later `commit`: commit per block (the generator does).
- vrnetlab creates switch NICs only up to the highest cabled port: removing servers breaks leaf configs — use `./up.sh light`, not `--node-filter`.
- The OcNOS console serves one client; an orphaned `telnet 127.0.0.1 5000` (e.g. left by the VS Code containerlab extension) blocks `con.py`.
- The first packets of a new flow through the PA-VM are often lost to ARP; retry before calling a failure.
- `wait` without arguments also waits for a `>(tee)` process substitution (bash 5): scripts that log themselves re-run under a pipe instead.
- iperf3 UDP to a multi-homed pod: bind the server to the rail address under test, otherwise replies leave from another rail.
- Nexus 9300v after the TCAM-carve reloads (2026-10-04): a vPC leaf can come back with a perfect control plane and an nve1 that decapsulates nothing
  (input counter stuck, half of the pings to its pair's servers lost from everywhere: the spines balance ICMP per packet). `nx-nve-heal.sh`.
- The storage management VIP announced itself only when it moved, i.e. at guest boot, before the fabric was up: `fb-vip.sh` now re-announces every 30 s.
- A Longhorn instance-manager pod left from an aborted boot stays Pending for ever (restartPolicy Never); `finish.sh` deletes it after 3 min.
- PAN-OS CLI: never run `show log ...` without a time filter (`receive_time in last-hour`): it walks the whole log and the CLI answers
  "Invalid user" to every other session until it is done.
- OcNOS `reload` on a rail leaf that has lost its L2 configuration (the memory-leak fault) first asks "The system has unsaved changes. Would you
  like to save them now? (y/n)". Answering yes writes the broken running config over the good saved one: three rail leaves lost their saved
  config that way on 2026-10-04 (the watchdog's old `reload, y, y`). `rail-restore.sh` reads the prompt and answers no.
- After about five hours and three acceptance runs in one boot every rail leaf was at its memory ceiling: this platform carries roughly one
  acceptance run per fresh set of rail leaves. `./rail-heal.sh all` before another long run.
- A rail leaf that has just been reloaded answers pings to its rail gateway only after it has resolved the asking node (seconds on the OcNOS
  VM). The validation asks from all 32 nodes at once: on 2026-10-04 that cost 8 "rail alignment" failures on be-leaf1, twelve minutes after its
  reload, with nothing wrong on the leaf (every node was answered when asked again; the re-run passed). `rail-restore.sh` now asks from every
  GPU node before it reports a leaf restored.
- The firewall has ONE active route towards the fabric per prefix (via fe-border1; the fe-border2 path is its second BGP path, no ECMP), while
  the fabric reaches the firewall through either border leaf. So a reply regularly comes back through the other border leaf than its request
  went in (e2e trace 2026-10-04: 3 of 3). Both hand-off sub-interfaces are in one zone, so the session matches; do not read it as a fault.
- A helper that records "command + raw output" for the audit transcript records a key too when the command prints one: `curl -v` shows the
  request headers, so the gateway key landed twice in `raw/commands.txt` of the first keyed trace (2026-10-04, scrubbed within minutes, the file
  never left the host). Redacting what the script itself writes is not enough: `trace.sh` now switches the transcript off while a keyed request
  runs, logs the redacted record instead, and scrubs every file of the result set at the end.
- A bare `wait` in a script that also runs background captures waits for the captures: wait for the job PIDs you mean.
- A `ggml-rpc-server` serves one client at a time: a second `llama-server --list-devices` against a busy worker blocks until the first lets go.

## Disaster recovery design
[`ai-fabric-dr-design.html`](ai-fabric-dr-design.html) (2026-10-02, profile `site-a-nx`; open in a browser): a second site for this design.
Two independent fabrics and clusters (`ai-fabric-a` / `ai-fabric-b`), L3-only VXLAN EVPN Multi-Site DCI with fe-border1/2 as anycast BGWs,
only VRFs `k8s` and a new `repl` (VLAN 400, L3VNI 14000) extended, no default route across the DCI (each site exits its own PA pair),
inference active/active behind a site-C GSLB witness, training active/standby from replicated checkpoints. Also: the DR gaps of this lab
(single PA-VM, backups on the storage node's own disk, dns-b + Root CA, Platform CA name constraints), site B addressing, traffic flows
F1-F6, failure analysis, runbooks and a build order. Design only: nothing in it is built or tested yet.
